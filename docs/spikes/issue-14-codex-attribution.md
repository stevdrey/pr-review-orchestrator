## Documented behavior and limits

OpenAI's [GitHub review guide](https://learn.chatgpt.com/docs/third-party/github)
documents the exact pull request comment `@codex review`, a reaction and subsequent
review, and repository connection and Code Review enablement as prerequisites.
It also documents automatic review settings, including personal preferences and
repository settings. These settings and the applicable trigger must be checked for
the test account. The guide does not establish that a GitHub App installation or
user access token comment is accepted, nor whose usage is charged in either case.
GitHub comment authorship alone cannot prove Codex entitlement or billing identity.

[OpenAI's pricing guide](https://learn.chatgpt.com/docs/pricing) classifies GitHub
reviews as Code Review usage and states that API-key-only access does not include
GitHub cloud code review. It does not establish which account is charged for this
experiment. A change in a shared or aggregated usage counter is not sufficient to
attribute a single review if concurrent activity or delayed reporting is possible.

### Minimal test App preparation

This is a temporary spike configuration, not the production webhook App:

1. Register a private GitHub App under the owner's account, with a unique name
   and this project's homepage. Enable device flow for explicit user authorization.
   Disable webhooks for this test; subscribe to no events.
2. Grant repository **Pull requests: read and write** (plus GitHub's automatic
   metadata read permission) and install it only on `stevdrey/dokene`. GitHub's
   [comment endpoint documentation](https://docs.github.com/en/rest/issues/comments#create-an-issue-comment)
   lists Pull requests write as one of the alternatives for both installation and
   user access tokens. Do not add Issues write or unrelated permissions for this test.
3. Generate the App private key securely for installation authentication. Treat it
   and all installation, user and refresh tokens as secrets; do not paste them into
   chat, command lines, logs or repository files. Use a short-lived secure client
   and revoke credentials and uninstall the test App when the experiment ends.
4. Use GitHub's [device flow](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app#using-the-device-flow-to-generate-a-user-access-token)
   for the owner to explicitly authorize the App. Verify the resulting actor and
   effective repository access independently before any comment. The App's client ID
   is not its private key. Never treat a GitHub actor as proof of Codex billing.

App creation, installation and authorization change security-sensitive access.
The owner must approve the precise scope before installation and complete any
credential or authorization steps securely. Do not substitute this temporary
configuration for the planned signed-webhook architecture.

## Controlled experiment

1. Select an open, ready, safe PR authored by a collaborator other than the owner,
   in an explicitly authorized repository. Record repository ID, PR URL, author,
   base and head SHAs, and test window. Confirm the diff contains no sensitive data.
   Stop if the head changes; do not use evidence from the previous SHA for the new one.
2. Confirm the intended GitHub App installation, repository access and minimum
   permissions; obtain explicit user authorization for the user-token case. Verify
   the Codex-connected GitHub identity, eligible ChatGPT account/workspace, repo
   connection and review settings. Record identifiers and settings, never tokens.
   Arrange a small approved spending limit and an operator able to inspect usage.
3. Run **one case at a time**, disabling or isolating automatic triggers for manual
   cases and avoiding concurrent Codex activity. Do not change the test SHA between
   cases. Record start/end times, review configuration, baseline usage and its
   granularity and reporting delay. A lack of per-review accounting may make billing
   attribution inconclusive even when a counter moves.
4. For each manual case, use the appropriate scoped credential through an approved
   ephemeral client to post exactly `@codex review` as a PR conversation comment.
   Do not put credentials in shell arguments, logs, screenshots, repository files or
   AI prompts. Record the API result, comment URL, author login/type and time; inspect
   independently via GitHub. Wait a bounded, pre-agreed interval and record reaction,
   review URL, reviewer, completion time and reviewed SHA or the observed failure.
   Never retry automatically; investigate ambiguity before another billable request.
5. Separately run native auto-review using the configured supported trigger and a
   fresh eligible event. Record the event, settings, review evidence and exact SHA.
   If a new commit is required, record the changed SHA and compare cases accordingly;
   do not pretend the tested inputs were identical.
6. For each case, have the authorized account operator inspect the relevant account
   or workspace's usage evidence after the provider's reporting delay. Record the
   account/workspace identifier in an appropriately private location, time window,
   units, source and correlation to the individual review if exposed. Confirm
   whether usage consumed included allowance, credits or another billing mechanism
   only if supported by evidence. Redact sensitive account details from public records.
7. Record each case's separate actor, trigger acceptance, reviewed SHA, entitlement
   and charge evidence. Mark attribution **inconclusive** if the provider exposes
   only aggregate counters or the account cannot be established. Preserve links to
   sanitized evidence and exact commands or UI steps, timestamps and limitations.
   Revoke any temporary credentials and restore settings after testing.

Before any write or provider call, reconfirm authorization, current head, budget and
that the corresponding case has not already run. Do not run tests against an
unrelated PR or turn on repository-wide auto-review without the owner's authorization.

## Decision and fallback

Until all three dimensions are independently demonstrated for a specific account,
installation and configuration, the orchestrator must leave this Codex request path
disabled. A user-token trigger succeeded in this experiment; the installation-token
request did not trigger a review in the observed configuration, without establishing
general incompatibility. An owner may request a review manually through a
documented, eligible workflow, or select a separately approved provider with
observable billing and budget controls. Native auto-review is an option only after
its configuration and accounting are verified; none of these fallbacks is currently
implemented by this service. Missing usage evidence requires a human handoff, not a
claim of free usage or permission to bypass budget gates.
