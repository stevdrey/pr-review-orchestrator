# Durable re-review planning from synchronize events

Issue [#72](https://github.com/stevdrey/pr-review-orchestrator/issues/72) connects signed GitHub deliveries to fix correlation, current-head CI and durable review intents. The worker uses the existing sandbox dispatcher for one explicitly selected PR in a single repository.

## Enable the planner

Enable signed webhook ingress and the [read-only sandbox CI worker](ci-and-iteration-policy.md#durable-sandbox-worker), then set `orchestrator.sandbox-ci.synchronize-enabled=true`. The existing sandbox PR, installation pair, repository and workflow IDs still apply. The configured SHA is the starting target for CI before tracking begins. Once a PR is tracked, the planner checks CI for its current head. The optional review evidence reader keeps its own configured SHA.

The read installation needs Pull requests, Actions and Contents read permissions. The adapter issues repository-scoped tokens for each operation and compares the root tree SHAs of the two [Git commit objects](https://docs.github.com/en/rest/git/commits#get-a-commit-object). The worker accepts same-repository PRs. Author notifications must be disabled. Review dispatch is disabled by default and has a separate opt-in described below.

Intent creation also requires a trusted `ReviewIntentPolicy` bean that allows the exact PR, provider, stage and SHA under local authorization and budget policy. Without a bean, the worker updates state and records CI evidence but denies new intents. The cap uses `orchestrator.codex.max-requests` (1–6, default 6). It includes existing request reservations and issued review intents that have yet to occupy a reservation slot. A cancelled intent no longer counts. A dead-lettered intent still counts because its effect may have landed.

## Processing and recovery

1. The durable worker claims an authorized delivery. It captures the local PR version and reads the PR through the configured read installation. Both scopes are rechecked when committing. The GitHub response must match the configured PR and repository and corroborate the delivery SHA. A delivery for another SHA completes without changing the tracked head.
2. An accepted synchronize uses the existing head transition and invalidates earlier clean and CI evidence. If remediation is waiting on the quiet period, the worker completes the signed delivery and schedules one internal assessment at the fix correlation deadline in the same transaction. Otherwise the synchronize reads current-head CI before it completes, so CI deliveries processed before it are not lost. The assessment is keyed by PR, head and quiet-period deadline. The synchronize and any CI wake-ups in the same quiet period share it. It keeps the first scheduler's correlation ID and receives its own bounded retry budget. Exact replays keep the original delivery and deadline. An assessment for a superseded SHA or quiet-period deadline completes without planning. A synchronize conflicts only with a newer head observation, not with unrelated state writes. Transaction conflicts are retried from fresh reads. This mode uses a 180-second claim lease. That covers the bounded PR, Git and CI reads, both transactions, and the token issues and revocations.
3. After the quiet period, the worker compares committed trees and obtains fresh current-head CI. Synchronize, check-run and workflow-run deliveries can wake the planner. Only passing CI, a reviewable PR, the existing remediation and disposition gates, available iteration capacity and a permitted intent can create a request. A current fix claim supports re-review while verification remains pending. A denial settles that delivery. A later qualifying signed synchronize or CI delivery can prompt a new assessment.
4. CI, the final eligibility check, the deduplicated `REQUEST_REVIEW` outbox write and inbox completion share a fenced transaction. The intent targets `codex` at `BASELINE` for the exact SHA. The outbox identity is unique across visits to that SHA. Historical reservations for the same target also suppress planning. Local version checks and the PR lock protect concurrent state, findings and iteration decisions.

Without the dispatch opt-in, the worker leaves outbox commands pending for inspection. Disable `synchronize-enabled` to return to pinned CI mode. Preserve the inbox and outbox records.

## Opt-in dispatch to Codex

[Issue #74](https://github.com/stevdrey/pr-review-orchestrator/issues/74) adds a worker for this sandbox PR's planned `codex` / `BASELINE` intents. Set `orchestrator.sandbox-ci.codex-dispatch-enabled=true` together with the dispatch, sandbox CI, synchronize and Codex enablement flags. The process still requires the single paired allowlist, read key, consenting `orchestrator.codex.actor-id`, notifications disabled and a dedicated approved `CodexUserCredentials` implementation. The terminal one-shot authorization and its temporary grant cannot be reused. Supply the local `ReviewIntentPolicy`, a `JdbcSandboxCodexBudget.Terms` bean for local hard budget reservations, and an approved `CodexApproval` that covers the planned trigger, entitlement and individual accounting. Startup fails without the budget terms. The repository ships without these approvals or credentials. See [Codex activation prerequisites](codex-review-requests.md#internal-contract-and-activation).

The planner stores the current head epoch with the intent. At dispatch, the fenced claim reuses the permanent request key. The request store rechecks the tracked head and epoch, passing CI, pending findings and required general feedback dispositions. The adapter revalidates live authorization, policy and budget and reads the open, non-draft PR's full SHA from GitHub before sending the fixed command. GitHub's comment endpoint has no atomic head condition. The adapter commits the receipt with head confirmation status first. A separate transaction under the PR lock then applies `START_REVIEW` for the same request and visit. If that step fails, the retry reconciles it from the committed receipt without posting again. A pause can land between the two transactions. The worker leaves the hold in place, and an authorized `RESUME` reconciles the unstarted receipt for the same head visit in the resume transaction. If the visit has changed, the old receipt cannot start a new review. The transition records that the request was sent. A clean verdict independently requires the exact reviewed SHA and authenticated completion.

The planned worker uses a bounded 40-second queue transaction to fence the row through the request store's independent transactions. If the outbox commit fails after a receipt was recorded, recovery reads the durable request and settles the existing command without posting again. A denied or stale request cannot post and settles the command as `CANCELLED`. A transient failure before the POST (GitHub or store unavailable, authorization authority unavailable, a draft PR, CI not yet passed or an unverified capability) keeps the permit `RESERVED`. Only the fenced planned worker may resume it, with bounded retries and backoff. If those retries run out, the command is dead-lettered and the reservation keeps occupying its iteration slot. An uncertain POST leaves the consumed permit in `ATTEMPTED` and the command in `DEAD/REMOTE_UNCERTAIN`. An `ATTEMPTED` row is never reused as a send permit. Keep the queue and request records for reconciliation.

V18 leaves pre-upgrade outbox rows without a recorded head epoch. The opt-in worker skips them because the current SHA alone cannot prove the original visit. They retain their original keys and continue to suppress duplicates. Newly planned intents record the visit in the same transaction as eligibility. Disable both Codex enablement and the dedicated dispatch flag to return to read-only planning.

Live provider completion and the review-to-notice cycle remain open in [issue #23](https://github.com/stevdrey/pr-review-orchestrator/issues/23).

## Verification

```sh
./gradlew --offline test --tests '*FeedbackLoopSandboxIntegrationTest' --tests '*DurableDispatchConfigurationTest'
./gradlew --offline clean build
git diff --check
```

The sandbox fixture uses signed HTTP ingress, disposable PostgreSQL, local Git commits and a loopback GitHub server. It covers exact replay, stale delivery, close pushes, concurrent claims, current-head CI, unresolved general feedback, revoked authorization, human hold, budget denial and the iteration cap. The planned dispatch tests use the actual adapter and exercise two competing workers, a POST with an ambiguous response, independent commit failures at `START_REVIEW` and at outbox settlement, a pause after the receipt commits, and a return to the same SHA on a newer visit. Persistent budget checks cover denial after an earlier hold exhausts the allowance, reuse of the hold after a transient read failure, retention after an ambiguous POST and replay after a recorded receipt. The fixtures make no calls to GitHub or Codex.

On 2026-11-26, the full build passed 357 tests, including 18 in the sandbox and dispatcher configuration suites, with zero failures or skips. `git diff --check` passed.

The [PR #73](https://github.com/stevdrey/pr-review-orchestrator/pull/73) regression `successfulFinalSynchronizeAttemptStillPlansAfterQuietPeriod` reproduced premature dead-lettering on `b3a506d` with four transient GitHub read failures followed by a successful final synchronize claim. The regression checks that the assessment stays pending until the quiet period ends, can retry its own transient failure, and creates one intent for the exact head without a new CI delivery.

Issue #74 verification on 2026-11-26 with JDK 27 and disposable PostgreSQL. `./gradlew --offline clean build` passed all 365 tests, including the 22 sandbox integration scenarios, with zero failures, errors or skips. `git diff --check` passed.
